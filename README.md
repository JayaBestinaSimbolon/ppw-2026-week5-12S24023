Analisis Kebutuhan & Kelayakan Web Services (Feasibility & SOAP)A. Komparasi Web Monolitik vs Web ServicesPada pengembangan sebelumnya (Minggu 1 s.d. Minggu 6), aplikasi SIPUS-Del dibangun sebagai sistem monolitik berbasis Server-Side Rendering (Blade Views) di mana peramban web (browser) bertindak sebagai satu-satunya konsumen antarmuka visual yang terikat erat dengan sesi server (stateful).Namun, seiring berkembangnya kebutuhan integrasi kampus—seperti peluncuran aplikasi Mobile Android/iOS bagi mahasiswa, integrasi Kiosk mandiri perpustakaan, hingga sistem administrasi yudisium berbasis legacy—arsitektur monolitik tidak lagi memadai karena:Pemisahan Domain (Domain Focus): Sistem backend harus mampu melayani berbagai platform klien (multi-client) secara seragam tanpa mencampuradukkan logika presentasi HTML.Komunikasi Antar-Mesin (Machine-to-Machine): Diperlukan standarisasi pertukaran data yang ringan dan cepat menggunakan format terstruktur seperti XML dan JSON.B. Peran Provider vs Consumer pada SIPUS-DelService Provider: SIPUS-Del bertindak sebagai penyedia layanan dengan mengekspos rute RESTful API (/api/v1/...) agar data katalog buku, kategori, dan transaksi sirkulasi dapat diakses secara aman dan terkontrol oleh aplikasi eksternal atau aplikasi mobile.Service Consumer: SIPUS-Del bertindak sebagai konsumen ketika mengonsumsi layanan eksternal (seperti memanggil OpenLibrary API atau GitHub REST API) untuk memperkaya metadata buku maupun data portofolio pengembang.C. Alasan Pemilihan REST dibanding SOAP untuk Aplikasi Mobile & KioskMeskipun sistem legacy perpustakaan atau perbankan masih menggunakan SOAP (yang berbasis XML kaku dengan amplop <soap:Envelope> dan kontrak WSDL formal), proyek modern seperti aplikasi mobile SIPUS-Del memilih arsitektur REST (Representational State Transfer) karena:Ukuran Payload Lebih Ringan: Format JSON jauh lebih ringkas dibanding XML SOAP yang verbose, sehingga menghemat kuota data dan mempercepat latensi jaringan seluler.Statelessness (Nir-Status): Tidak membebani memori server dengan penyimpanan sesi pengguna; setiap request berdiri mandiri dengan membawa token autentikasi (Bearer Token).Kesesuaian Standar Web: Memanfaatkan penuh metode semantik HTTP (GET, POST, PUT, PATCH, DELETE) dan kode status standar industri secara alami.🏛️ 2.
